用户通过连连看收集花材，再搭配一束花，生成可以保存或带入小红书笔记发布页的作品卡。首版验证“解谜之后完成一件属于自己的作品”能否带来主动重玩和分享意愿。以下范围、数量和实验门槛均为本版提案；用户需求与增长效果仍需实际验证。

# 产品定位与目标用户

面向喜欢花卉、视觉搭配、轻度解谜的用户，首批招募以小红书相关兴趣的女性用户为主。典型场景是午休、通勤或睡前，用几分钟完成一次轻松的游戏与创作。

首版目标是让用户不需要额外注册、学习复杂规则或等待养成，就能完成第一束花。单轮“连连看至生成作品卡”的目标体验时长为2至5分钟，不设倒计时失败。

核心假设：

- 连连看的花材奖励能让用户愿意继续完成花束创作。

- 用户在花材、包装和祝福语上作出选择后，更愿意保存或分享作品。

- 用户完成第一束后，会因想换一种搭配而主动重玩。

# 用户流程与页面

开始页 → 连连看 → 清盘收花 → 搭配花束 → 生成作品卡 → 保存或分享 → 再做一束

| 页面 | 主要内容 | 关键操作 |
| --- | --- | --- |
| 开始页 | 产品一句话介绍、开始按钮、可恢复的进度、最近作品入口 | 开始、继续、查看作品 |
| 游戏页 | 棋盘、已消除对数、当前收集花材、提示、音效开关 | 选择两朵花、提示、重开 |
| 搭配页 | 花束预览、5个花位、花材数量、包装与丝带选项 | 选花位、放入或替换花材、生成作品卡 |
| 作品页 | 作品卡、祝福语、保存与分享入口 | 修改祝福语、保存、分享、返回搭配、再做一束 |

开始页不自动进入计时或播放音乐。首次进入游戏，用可跳过的短教学演示“相同花朵、空路连接、最多两个转弯”。教学操作不额外发放奖励，也不改变正式盘面。

“再做一束”创建新一局，优先选择不同的初始布局；旧作品仍可从最近作品中查看。查看旧作品不重新发放花材。

# 连连看规则

棋盘为6行6列，共36张牌。6种花材各6张，每种可组成3对；每局最多获得每种花材3枝，共18枝。花材暂定为玫瑰、郁金香、雏菊、向日葵、绣球、满天星，最终以小尺寸辨识效果决定。

连接规则：

- 两张牌必须是同一种花材。

- 路径只能沿横向或纵向经过空格，最多转两个弯。

- 棋盘外保留一圈空路径，允许绕行。

- 第二次点击同一张牌取消选择；点击不同且无法连接的牌，保留第二张为当前选择，并给出轻反馈。

- 成功连接后播放简短消除动画；本对结算完成前不接受下一对输入。

每对消除只结算一次。动画、回到前台或恢复进度不能重复获得花材。清盘后自动进入收花确认，展示本局18枝花材，再进入搭配页。

提示高亮一对当前可连接的牌，不自动消除、不扣奖励。若仍有牌但没有合法配对，自动重排剩余牌，保留花材种类与数量、已消除对数及已有奖励。重排必须有次数上限；达到上限时切换至保证可继续消除的布局，不能无限重试或静默清空进度。

默认不设连击、金币、星级或排行榜。用时只作个人记录，不用于解锁花材或限制创作。

# 花束搭配与作品卡

花束采用5个固定花位，用户点击一个花位后选择花材，可随时替换。每放入1枝，当前可用数量减1；替换或移除时退回原花材。任何花材使用量不得超过该局获得数量。

5个花位填满后可生成作品卡。包装纸与丝带免费切换，不消耗花材；首版不提供自由拖拽、缩放、旋转或复杂图层编辑。离开后回来应保留上次选择。

作品卡固定为3:4竖图，目标导出尺寸1080×1440。卡片包含花束、日期、祝福语和低干扰产品署名，不显示用户头像或昵称。祝福语限20个字符，首版默认“送给今天的自己”，允许修改或清空；用户输入按普通文字渲染，不作为HTML或脚本执行。

生成作品卡后保留可编辑配方，重新生成不会重复扣花材。最近作品保留3份配方和日期，图片按需重新渲染，不依赖长期有效的临时文件路径。

保存和分享均由用户主动点击触发。分享只带入作品图和可编辑文案，不自动发布、不强制关注、不要求分享解锁。默认笔记标题可用“今天给自己做了一束花”，发布前由用户自行编辑和决定。

# 视觉与操作要求

视觉以自然花色、清晰轮廓和留白为主。花材不仅靠颜色区分，也要有明显不同的形状；棋盘上的花朵与花束中的花材使用一致的视觉特征。

- 按320、375、390和430 CSS像素宽度检查竖屏布局，主要页面不得横向滚动。

- 棋盘单格实际可点击区域不小于44×44 CSS像素，避开原生关闭按钮和底部安全区。

- 移动端仅需点按，核心操作不依赖悬停、双击或长按。

- 消除动画目标时长为150至300毫秒；减少动态效果时仍能明确识别操作结果。

- 音效可关闭，开关本地保存；首版不播放持续背景音乐。

- 页面切到后台后暂停动画和用时记录，恢复时不快速补播积压操作。

所有画面、花材、字体、声音和卡片元素须有可用授权，复用第三方代码时保留其许可要求。

# 平台边界与异常处理

依据[小工具官方能力清单](https://miniapp-sandbox.xiaohongshu.com/minitool/doc)，使用纯HTML、CSS、JavaScript和Canvas实现；所有图片、字体与静态数据随包交付。不得依赖外部请求、CDN、iframe、WebAssembly或自建实时服务。首版不依赖仍在内测的排行榜、云存储能力。

本地进度优先使用平台Storage API。每对消除完成、每次配方变更和生成作品时保存一致的状态；低版本做兼容降级。存储不可用时本局仍可继续，明确提示退出后可能无法恢复，不能显示“已保存”。本地记录不承诺永久保留或跨设备同步。

| 情况 | 用户行为与恢复结果 |
| --- | --- |
| 首次加载资源失败 | 显示重试，避免空白页面 |
| 重新打开已有进度 | 可继续游戏或搭配，也可确认后重开 |
| 进度损坏或版本不兼容 | 说明该局无法恢复，提供新开局；尽量保留可读取的作品配方 |
| 渲染或导出失败 | 保留配方，可重试，不清空花材与作品 |
| 相册权限拒绝或保存失败 | 提示未保存，可重试或返回作品页 |
| 分享能力不可用 | 隐藏不可用入口或说明当前不支持，保留相册保存途径 |
| 低版本客户端 | 对不可用能力降级；必要时提示更新，核心游戏仍可玩 |
| 重复点击或快速切后台 | 不重复消除、领奖、扣花材或触发多个导出任务 |

使用公开的窗口信息接口处理安全区；导出及发布能力调用前做版本和方法检测，并处理失败。分享发布页打开、用户点击发布和最终审核通过是不同状态，界面与数据记录不得混淆。

当前上传页面显示ZIP上限10MB，首版包体内部目标不超过5MB；实际发布以当次上传页的最新口令、校验与限制为准。

# 验证计划与数据口径

首轮招募20名符合目标兴趣的用户，观察首次体验，并在次日询问是否再次主动打开。以用户知情同意的试玩观察、问卷和人工记录为主；不接入外部分析SDK，也不假设创作者后台能够提供工具内每一步漏斗。

首版仅在本地记录必要的阶段状态，用于恢复与受邀试玩核对：开始、清盘、生成花束、保存结果、分享入口使用。平台后台如果有可核验数据，再补充分析。未拿到的数据标记未测，不填0。

| 指标 | 明确口径 | 首轮继续投入门槛 |
| --- | --- | --- |
| 清盘完成率 | 完成首次棋盘人数／20名开始试玩者 | 至少15人 |
| 花束完成率 | 生成第一张作品卡人数／20名开始试玩者 | 至少12人 |
| 保存或实际分享 | 成功保存或人工确认发布人数，按人去重／20人 | 至少6人 |
| 主动再玩 | 无额外奖励或研究者要求，主动开启第二局的人数／20人 | 至少8人 |
| 次日回来 | 次日实际再次使用，或用户明确自报使用的人数／20人 | 至少5人，并注明证据来源 |

以上是小样本实验门槛，不是行业基准或统计显著性结论。打开分享入口仅计分享意向，不计实际发布；保存失败与取消发布均不计成功。

若清盘完成率低，先修教学、操作或盘面难度。若清盘高但花束完成率低，验证用户是否需要创作环节。若花束完成高但保存分享低，先检查成品视觉和表达价值，避免用强制分享补指标。若重玩和次日回来都弱，暂不扩展养成和付费。

笔记曝光、点赞、收藏与工具内完成行为分开记录，不把曝光当玩家数，也不把收藏当留存。

# 验收标准

以下为实施前定义的端到端验收场景，当前尚未执行。完成开发后，必须在真实小红书容器中检查核心链路，普通浏览器预览和模拟SDK不能代替平台验证。

| 场景 | 通过条件 |
| --- | --- |
| 完整首局 | 从开始页清盘，18对正确结算，进入搭配并生成作品卡 |
| 连接规则 | 验证直线、一个转弯、两个转弯、外圈绕行、三转弯拒绝及障碍阻挡 |
| 无可消组合 | 自动恢复到可继续状态，不丢牌、不增减奖励、不出现无限重排 |
| 重复操作 | 连续点击、动画中点击、后台恢复均不重复结算 |
| 搭配数量 | 每种花材最多使用已获得数量；替换退回正确，未满5枝不能生成 |
| 保存恢复 | 游戏中途和搭配中途退出后，恢复一致；损坏状态给出明确恢复入口 |
| 导出作品 | 真机相册中有完整3:4图片，文字和花材不裁切，无原生控件被误导出 |
| 分享控制 | 用户主动打开笔记编辑页，可编辑或取消；取消后作品仍可继续保存 |
| 失败恢复 | 权限拒绝、导出失败、接口缺失时可返回操作，不丢配方 |
| 设备与版本 | 当前支持版本的iOS与Android各完成一轮；低版本不可用能力有降级 |

每次正式验收保留可重复的布局编号、操作步骤、客户端与设备版本、全流程录屏，以及一张实际导出的作品图。验收材料不包含账号凭证；公开分享的录屏遮盖无关个人信息。

# 实施顺序与待验证事项

1. 先做一个完整可玩的棋盘和一套花束模板，打通真实容器中的保存及分享。

2. 校验消除规则、重排、奖励一致性和进度恢复，再补齐3个布局与首版素材。

3. 完成端到端验收后，开展20人试玩；依据漏斗和访谈决定是否扩展。

正式实现前需确认：花材在小棋盘上的辨识效果、固定5花位的搭配是否足够有趣、目标设备的导出性能，以及作品卡是否值得用户保存。
